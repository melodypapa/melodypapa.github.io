## 1. 简介

### 1.1. 本文档的范围

本文档收集对诊断提取（**Diagnostic Extract**）的需求。

诊断提取的主要目标是在参与诊断开发过程的各方之间交换诊断数据，以支持诊断模块 **DCM** 和 **DEM** 的自动代码生成过程。

此外，诊断提取还用于支持诊断功能的分布式开发过程。

下面再次列出诊断提取使用中的关键方面：

- 为 **DCM** 和 **DEM** 交换诊断数据
- 支持诊断功能的分布式开发

### 1.2. 文档约定

**AUTOSAR** 文档中需求的表示遵循 TPS\_STDT\_00078 所规定的表格，参见标准模板（**Standardization Template**）的「追溯支持」（**Support for Traceability**）一章（[\[1\]](#ref-1)）。

应使用 TPS\_STDT\_00053 中规定的用于表达义务的助动词形式来表示需求，参见标准模板（**Standardization Template**）的「追溯支持」（**Support for Traceability**）一章（[\[1\]](#ref-1)）。

### 1.3. 指南

应引用既有的规范（以单个需求的形式）。与这些规范的差异作为附加需求加以规定。所有需求应具有以下特性：

- 无冗余（**Redundancy**）

  在单个需求之内或其他需求之中，需求不应重复。

- 清晰性（**Clearness**）

  所有需求应只允许一种解释。所使用的不在术语表中的技术术语必须加以定义。

- 原子性（**Atomicity**）

  每个需求应只包含一个需求。如果一个需求不能再被拆分为更多的需求，则它是原子的。

- 可测试性（**Testability**）

  需求应能通过分析、评审或测试加以验证。

- 可追溯性（**Traceability**）

  需求的来源和状态应始终可见。

### 1.4. 需求追溯

本文档目前不提供需求追溯。需求追溯将在后续修订版中加入。

## 2. 需求

### 2.1. 与 AUTOSAR 特性的关系

本节描述需求应当覆盖的特性列表：

- **AUTOSAR** 应提供数据交换格式，以支持大型跨公司和公司内部开发团队之间的协同工作（**work-share**）
- **AUTOSAR** 应为引导加载程序（**boot loader**）提供接口
- **AUTOSAR** 服务应支持系统诊断功能

这是诊断提取需求需要满足的特性和主要需求的一个简短节选。

### 2.2. 通用需求

本章包含一组适用于诊断提取所有方面的通用需求。

#### 2.2.1. 诊断数据交换（**Diagnostic data exchange**）

| 描述 | 诊断提取应支持诊断相关信息的交换。 |
| --- | --- |
| 理由 | 在绝大多数情况下，**AUTOSAR** 诊断栈的配置是 **OEM** 与相应 **ECU** 供应商共同完成的工作。为此，**OEM** 和供应商需要能够以尽可能小的摩擦交换配置信息。一般而言，特定 **OEM** 与特定供应商的任意组合都是可能的。要使之可行，就必须在必要的程度上标准化相关各方之间交换的数据。 |
| 用例 | 1. **OEM** 向供应商交付部分配置，期望供应商填入缺失的部分和/或评审并（在适用时）覆盖 **OEM** 已完成的配置。<br>2. 供应商将评审后的诊断配置反馈给 **OEM**。<br>3. 供应商将诊断栈的最终配置交付给 **OEM**，使后者能够从该数据推导出测试仪（**tester**）配置。<br>4. 供应商或 **OEM** 使用诊断提取在公司内部的相关责任组织部门之间交换信息。以此方式支持公司内部的分布式软件开发。 |
| 依赖项 | - |
| 支撑材料 | - |

#### 2.2.2. 相关 ECU-C 参数的推导（**Derivation of related ECU-C parameter**）

| 描述 | 诊断提取应支持为 **Dcm**、**Fim** 和 **Dem** 推导相关的 **ECU-C** 参数。 |
| --- | --- |
| 理由 | 就定义而言，**ECUC** 层级上 **AUTOSAR** 诊断栈的具体配置是不可移植的。它非常聚焦于反映特定诊断栈具体实现的细节。这种做法是合理的，因为它允许比通用且更抽象的方法更深入地优化软件栈。然而，更抽象的方法在跨不同组织乃至一定程度上跨项目的可交换性方面有其他优势。因此，合理的做法是为诊断栈的配置定义一种通用的、更抽象的方式，其最终目标是在很大程度上推导出具体的、不可移植的特定配置。 |
| 用例 | 用户希望以一种可以与项目伙伴交换的通用方式规定诊断栈的配置，交换方式类似于例如系统描述的交换。用户希望在与系统提取相同的概念层级上规定诊断信息，并且希望在适用时从诊断配置关联到系统提取的元素。最后，用户希望获取这一在较高概念层级上描述的信息，并将其用于推导 **ECUC** 这一具体得多（因而不太可移植）层级上的配置信息。 |
| 依赖项 | - |
| 支撑材料 | - |
