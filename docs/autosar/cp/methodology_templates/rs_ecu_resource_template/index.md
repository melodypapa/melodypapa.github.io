## 1. 文档范围

本文档收集对 ECU 资源模板（**ECU Resource Template**，**EcuR**）的需求。

EcuR 的主要目标是提供 ECU 资源描述（**ECU Resource Description**）的方案。ECU 资源描述 [\[1\]](#ref-1) 保存用于构建 **AUTOSAR** 系统的硬件组件的相关信息。

EcuR 的范围涵盖：

- 处理单元
- 存储器段
- IO 与通信外设
- 微控制器
- ECU 电子部件
- 传感器和执行器（既包括 ECU 外壳内部的，也包括外部连接到 ECU 的）

EcuR 的一种用途是通过提供关于可用硬件资源及其连接的信息来支持系统设计：

- 每个 ECU 上可用的微控制器/处理器内核
- 每个 ECU 上可用的存储器
- 每个 ECU 上可用的总线通信接口

另一种用途是通过提供关于硬件及其连接的详细信息来支持 ECU 配置（**ECU Configuration**）[\[2\]](#ref-2)：

- ECU 电子部件如何连接到微控制器外设
- 哪个微控制器内核可以访问哪个存储器和外设

### 1.1. 文档约定

**AUTOSAR** 文档中需求的表示遵循 TPS\_STDT\_00078 所规定的表格，参见标准模板（**Standardization Template**）的「追溯支持」（**Support for Traceability**）一章（[\[3\]](#ref-3)）。

应使用 TPS\_STDT\_00053 中规定的用于表达义务的助动词形式来表示需求，参见标准模板（**Standardization Template**）的「追溯支持」（**Support for Traceability**）一章（[\[3\]](#ref-3)）。

## 3. 需求

### 3.1. 通用需求

#### 3.1.1. 支持基础软件的配置

**ECU** 资源模板应提供用于描述硬件属性的方法，这些属性支持 **AUTOSAR** 基础软件的配置。

| 描述 | **ECU** 资源模板应提供用于描述硬件属性的方法，这些属性支持 **AUTOSAR** 基础软件的配置。 |
| --- | --- |
| 理由 | 部分 **ECU** 配置参数的取值可以从已配置硬件的 **ECU** 资源描述中推导得出。 |
| 用例 | **ADC** 通道的最大数量由可用硬件决定，因此可以从 **ECU** 资源描述中推导得出。 |

| 支撑材料 | - |

### 3.2. 描述专用硬件的需求

#### 3.2.1. 处理单元规范

**ECU** 资源模板应提供专门的方法来描述处理单元。处理单元应定义为微控制器/处理器的内核。

| 描述 | **ECU** 资源模板应提供专门的方法来描述处理单元。处理单元应定义为微控制器/处理器的内核。 |
| --- | --- |
| 理由 | 处理单元的数量对系统和 **ECU** 的设计至关重要。 |
| 用例 | * 为了将软件执行的上下文映射到各个内核，需要了解各个内核。<br>* 在双核微控制器中，部分存储器段只能被一个内核访问。通过对各个内核的专门描述，可以刻画对这些存储器段的访问。 |
| 依赖项 | - |
| 支撑材料 | - |

#### 3.2.2. 可用存储器

**ECU** 资源模板应提供专门的方法来描述存储器段。这包括所有可能的存储器种类，如 **RAM**、**ROM**、**EEPROM**、**Flash** 等。

| 描述 | **ECU** 资源模板应提供专门的方法来描述存储器段。这包括所有可能的存储器种类，如 **RAM**、**ROM**、**EEPROM**、**Flash** 等。 |
| --- | --- |
| 理由 | 存储器段的数量及其属性对系统和 **ECU** 的设计至关重要。 |
| 用例 | * 需要了解可用存储器容量，才能将软件分配到系统中的不同 **ECU**，并从存储器角度检查软件是否能够放下。<br>* 在链接器运行期间，软件的存储器需求会被映射到实际可用的硬件存储器上。为支持这一活动，应为每个 **ECU** 描述其存储器段。<br>* 在多核微控制器中，部分存储器段只能被一个内核访问。通过对各个内核的专门描述，可以刻画对这些存储器段的访问。 |
| 依赖项 | - |
| 支撑材料 | - |

#### 3.2.3. 可用通信手段

**ECU** 资源模板应提供专门的方法来描述通信硬件。

| 描述 | **ECU** 资源模板应提供专门的方法来描述通信硬件。 |
| --- | --- |
| 理由 | **ECU** 的通信至关重要，应与系统描述和 **ECU** 配置以协调的方式一起描述。 |
| 用例 | * 描述用于系统描述以及 **ECU** 之间通信设计的网络端口。<br>* 描述不属于系统描述的网络端口（用于访问智能传感器/执行器的本地网络端口）。 |
| 依赖项 | - |
| 支撑材料 | - |

#### 3.2.4. 可用 IO 硬件外设

**ECU** 资源模板应提供专门的方法来描述 IO 硬件外设（**IO-HW-Peripherals**）。

| 描述 | **ECU** 资源模板应提供专门的方法来描述 IO 硬件外设（**IO-HW-Peripherals**）。 |
| --- | --- |
| 理由 | 不同的 IO 硬件外设需要专门的方法，从硬件角度描述其属性；不同的 IO 硬件外设还需要专门的方法，描述其在微控制器内部以及对外部的连接。 |
| 用例 | * 微控制器引脚 87 上提供 **ADC** 通道 5。<br>* 变体管理：如果微控制器被配置为在引脚 53 上提供 **ADC** 通道 7，则 **DIO** 无法将引脚 50–57 用于其自身用途。 |
| 依赖项 | [§3.1.6](#316-描述硬件的可变性) |
| 支撑材料 | - |

#### 3.2.5. IO 硬件抽象规范

**ECU** 资源模板应通过 IO 硬件抽象层（**IO-HW-Abstraction**）提供硬件传感器/执行器与 IO 硬件外设之间的抽象连接信息。

| 描述 | **ECU** 资源模板应通过 IO 硬件抽象层（**IO-HW-Abstraction**）提供硬件传感器/执行器与 IO 硬件外设之间的抽象连接信息。 |
| --- | --- |
| 理由 | 为了配置 IO 硬件外设，必须了解连接了哪些传感器/执行器，以及 IO 硬件抽象层将如何访问相应的 IO 硬件外设。 |
| 用例 | * 转速传感器通过复杂的电子部件连接到微控制器引脚 53 的 **ADC** 通道 7 的 IO 端口。复杂电子部件的行为不做描述，但应规定连接本身，从而使 IO 硬件抽象软件的实现者能够获得正确的连接信息。<br>* 收发器电子部件连接到 **Can** 总线，与 **Can** 通信控制器存在连接，为启用通信而连接到 **DIO** 通道 8（引脚 47），并为发起唤醒而连接到 **DIO** 通道 5（引脚 87）。 |
| 依赖项 | - |
| 支撑材料 | - |
