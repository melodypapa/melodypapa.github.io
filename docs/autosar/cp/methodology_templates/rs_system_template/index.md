## 1. 文档范围

本文档收集对系统模板（**System Template**，**SYS-T**）的需求。系统模板的主要目标是定义系统的纯软件视图与带有联网 **ECU** 的物理系统架构之间的关系。

系统模板涵盖以下领域：

- 系统拓扑：在系统拓扑中描述系统的逻辑布局。也就是说，记录哪个 **ECU** 连接到哪个簇（**cluster**）或信道（**channel**）。
- 通信属性：通信系统的中心目的是交换具有特定属性的帧。
- 映射：映射涵盖软件组件到 **ECU** 的分配，以及要在软件组件之间交换的数据元素到信号和帧的映射。

本文档中收集的需求将由系统模板规范 [\[1\]](#ref-1) 满足。该文档实现了本文所述的大部分需求。

### 1.1. 文档约定

**AUTOSAR** 文档中需求的表示遵循 TPS\_STDT\_00078 所规定的表格，参见标准模板（**Standardization Template**）的「追溯支持」（**Support for Traceability**）一章（[\[2\]](#ref-2)）。

应使用 TPS\_STDT\_00053 中规定的用于表达义务的助动词形式来表示需求，参见标准模板（**Standardization Template**）的「追溯支持」（**Support for Traceability**）一章（[\[2\]](#ref-2)）。

## 2. 需求

### 2.1. 类别：主要需求

#### 2.1.1. AUTOSAR 模板之间的兼容性

兼容性（**Compatibility between the AUTOSAR Templates**）

| 描述 | 必须保证 **AUTOSAR** 各模板之间的兼容性。在此语境下，兼容性意味着每个 **AUTOSAR** 模板都可以包含对另一个 **AUTOSAR** 模板元素的引用。 |
| --- | --- |
| 理由 | 确保 **AUTOSAR** 各模板之间的连贯性和互操作性。 |
| 依赖项 | 未识别到。 |
| 用例 | 使用同一工具链开发车载电子架构（软件建模、硬件建模和映射约束建模）。 |
| 支撑材料 | - |

### 2.2. 类别：系统模板需求

#### 2.2.1. 传统系统

混合系统（AUTOSAR/非 AUTOSAR）（**Mixed Systems (AUTOSAR/NON-AUTOSAR)**）

| 描述 | 因使用混合系统而产生的系统约束，必须由系统模板处理。 |
| --- | --- |
| 理由 | 从非 **AUTOSAR** 系统到全 **AUTOSAR** 系统的过渡只能逐步实现。此外，必须确保与传统解决方案的互操作性。因此，必须允许 **AUTOSAR** **ECU** 和非 **AUTOSAR** **ECU** 同时存在于同一系统（「混合」系统）中。 |
| 依赖项 | 未识别到。 |
| 用例 | 在既有架构中逐步引入 **AUTOSAR**，例如，应可以处理并非源自 **AUTOSAR** 软件组件的信号。 |
| 支撑材料 | - |

#### 2.2.2. 基础软件与 RTE 资源

基础软件资源与 RTE 资源（**Basic Software Resources and RTE Resources**）

| 描述 | 系统模板必须涵盖基础软件和 **RTE** 的资源请求。 |
| --- | --- |
| 理由 | **ECU** 的资源就其自身定义而言是有限的（**RAM**、**ROM**、**CPU** 时间等）。这些限制在映射过程中充当约束。 |
| 依赖项 | 未识别到。 |
| 用例 | 在小型 **ECU** 上分配 **AUTOSAR** 服务和特性时考虑存储器限制。 |
| 支撑材料 | - |

#### 2.2.3. 迭代式开发

迭代式开发（**Iterative Development**）

| 描述 | 系统模板必须支持迭代的系统开发。 |
| --- | --- |
| 理由 | 在 **AUTOSAR** 系统的开发过程中，系统设计过程前几个步骤中找到的解决方案本身会成为后续系统生成步骤的系统约束。 |
| 依赖项 | 未识别到。 |
| 用例 | 如果在开发的后期阶段向车辆项目添加新功能，当前的映射本身会成为与新功能相关的新软件组件映射的约束。 |
| 支撑材料 | - |

#### 2.2.4. 软件组件到 ECU 的映射

软件组件到 ECU 的映射（**Mapping of Software Components to ECUs**）

| 描述 | 系统模板必须描述软件组件到 **ECU** 的映射。还应可以可选地将软件组件映射到一个 **ECU** 内的各个处理单元。 |
| --- | --- |
| 理由 | - |
| 依赖项 | 未识别到。 |
| 用例 | 出于安全原因（或仅仅凭经验），某些特定的软件组件只能运行在特定的 **ECU** 上。这种「预映射」是实际映射过程的约束。 |
| 支撑材料 | - |

#### 2.2.5. 软件组件到 ECU 的映射：聚簇

SWC 簇（**SWC Cluster**）

| 描述 | 系统约束描述必须涵盖软件组件的聚簇。软件组件聚簇意味着两个软件组件不可拆分，必须映射到同一个 **ECU**。 |
| --- | --- |
| 理由 | 由于性能需求、安全通信需求或仅仅凭经验，必须防止某些通信路径被映射到外部总线上。此时涉及的软件组件应一起映射到同一个 **ECU**。 |
| 依赖项 | 未识别到。 |
| 用例 | 不能经由通信总线进行的安全通信，或非常严格的时序要求。 |
| 支撑材料 | - |

#### 2.2.6. 软件组件到 ECU 的映射：分离

SWC 分离（**SWC Separation**）

| 描述 | 系统约束描述必须涵盖软件组件的分离。软件组件分离意味着两个软件组件不能位于同一个 **ECU** 上。 |
| --- | --- |
| 理由 | 增强冗余 **SWC** 的独立性。 |
| 依赖项 | 未识别到。 |
| 用例 | 出于安全需求，实现安全关键功能的两个冗余软件组件不会一起映射到同一个 **ECU** 上（当然，冗余并不总是意味着 **SWC** 分离）。 |
| 支撑材料 | - |

#### 2.2.7. 拓扑描述

拓扑（**Topology**）

| 描述 | 系统模板必须描述 **EE** 系统的拓扑。 |
| --- | --- |
| 理由 | 可用的通信路径限制了软件组件到某些 **ECU** 的可能分布。 |
| 依赖项 | 未识别到。 |
| 用例 | 从功能角度紧密关联的软件组件的映射：此时必须了解拓扑，以避免过长的数据路径。 |
| 支撑材料 | - |

#### 2.2.8. 数据分段

数据分段（**Data Segmentation**）

| 描述 | 系统模板必须提供可用于将（应用）数据分段到多于 1 个帧的信息。 |
| --- | --- |
| 理由 | 底层总线技术的数据长度限制。 |
| 依赖项 | 未识别到。 |
| 用例 | 诊断数据的传输，其长度通常超过特定总线的最大帧大小。 |
| 支撑材料 | - |

#### 2.2.9. 总线带宽

总线带宽（**Bus bandwidth**）

| 描述 | 系统模板应支持带宽计算，作为通信矩阵（**Communication Matrix**）定义的约束。 |
| --- | --- |
| 理由 | 带宽是有限资源，在通信矩阵的定义过程中充当约束。 |
| 依赖项 | 未识别到。 |
