## 1. 文档范围

以下规范定义 **AUTOSAR** 日志与跟踪（**Log and Trace**，**LT**）的功能和非功能需求。

本文档的焦点是规定以下内容的需求：

- **LT** 到其他 CP:BSW 模块 / AP:功能集群的接口
- 到 CP:RTE/VFB / AP:ARA 跟踪的接口
- 到 CP:SWC / AP:应用的接口
- 日志和跟踪消息的传输与存储格式
- 到 **LT** 通信模块的内部接口
- **LT** 的通用配置

本文档不规定以下内容的需求：

- 通过 **LT** 通信模块进行通信的传输层

## 2. 所用约定

**AUTOSAR** 文档中需求的呈现遵循 TPS_STDT_00078 中规定的表格，参见 **AUTOSAR** 标准化模板 [\[1\]](#ref-1) 的「可追溯性支持（**Support for Traceability**）」章节。

应使用 TPS_STDT_00053 中规定的表达义务的言语形式来表示需求，参见 **AUTOSAR** 标准化模板 [\[1\]](#ref-1) 的「可追溯性支持」章节。

## 3. 缩略语和缩写

以下词汇表包含与诊断日志和跟踪（**Diagnostic Log and Trace**）模块相关、且未包含在 [\[2\]](#ref-2) 中的缩略语、缩写和定义。

**Log and trace message**
> 日志和跟踪消息包含在软件中指定一个日志和跟踪事件所需的全部数据和选项。

**User**
> **LT** 的用户是使用 **LT API** 生成日志和跟踪消息的软件程序员。

**Log**
> 用户按需生成日志消息。每当用户想展示关于状态变化或值变化的某些信息时，他就向 **LT** 添加一个 **API** 调用。

**Trace**
> 跟踪消息可以通过对代码插桩生成（例如 **VFB** 跟踪）。被插桩的代码调用 **LT** 的 **API**。

**ECU ID**
> **ECU ID** 是每个 **ECU** 的名称。

**Session ID**
> 会话 **ID** 是一个日志或跟踪会话的标识编号。如果一个应用被多次实例化，则日志会话会获得一个新的会话 **ID**。一个应用可以拥有多个日志或跟踪会话。一个 **BSW** 模块使用模块编号作为会话 **ID**。

**Application ID**
> 应用 **ID** 是应用/**BSW** 模块的短名称。它在日志和跟踪消息中标识该应用/**BSW** 模块。

**Context ID**
> 上下文 **ID** 是用户定义的 **ID**，用于将由一个应用/**BSW** 模块产生的日志和跟踪消息分组，以区分不同的功能。每个应用 **ID** 可以拥有多个上下文 **ID**。上下文 **ID** 按应用 **ID** 分组。上下文 **ID** 在一个应用 **ID** 内应当唯一。日志和跟踪消息来源的识别通过一对应用 **ID** 和上下文 **ID** 完成。

**Message ID**
> 消息 **ID** 是用于刻画消息自身所携带信息的 **ID**。一个消息 **ID** 唯一地标识一条日志或跟踪消息。它可用于识别消息的来源（在源代码中），也可用于刻画消息的载荷。

**Log and trace level**
> 日志级别为日志消息的严重程度定义了一个分类。跟踪状态提供是否应发送跟踪消息的信息。

**Time**
> 每条日志和跟踪消息都可以包含一个时间属性。该时间属性是一个自由定义的时间值。它是自 **ECU** 启动以来的时间。

**External client**
> 外部客户端是一种工具，它可以运行在 **PC** 或另一台 **ECU** 上，并通过 **DCM** 或 **LT** 通信模块连接到 **LT**。

## 4. 需求规范

本章描述驱动在 **AUTOSAR** 中定义日志与跟踪（**Log and Trace**）工作的所有需求。

### 4.1. 功能概述

**LT** 为应用和其他模块提供通用的日志与跟踪功能。

总体上，**LT** 提供以下功能：

- 日志
  * 对来自 **AUTOSAR** 应用的错误、警告和信息消息进行日志记录，提供一个标准化的 **AUTOSAR** 接口
  * 将来自所有 **AUTOSAR** 应用层级和中间件层级的全部 **LT** 消息汇集到一个集中式的 **AUTOSAR** 模块（**DLT**）中。
  * 来自 DET [\[3\]](#ref-3)、DEM [\[4\]](#ref-4) 的日志消息（经典平台）
- 跟踪
  * 跟踪 RTE/VFB（[\[5\]](#ref-5)）（经典平台）
- 控制
  * 启用/禁用单条 **LT** 消息
  * 通过反向通道逐个控制跟踪级别
- 通用性
  * **LT** 在调试阶段和生产阶段均可用
  * 通过标准诊断或平台特定的测试接口访问
  * 防止在生产阶段被滥用的信息安全机制

此外，为自适应平台提供以下功能：

- 时间戳
  * 如果需要时间戳，**LT** 模块提供对日志消息和跟踪消息都加时间戳的可能性。
  * 这种加时间戳由 **LT** 模块直接处理，无需应用的任何干预。
- 应用通信跟踪
  * **LT** 模块能够处理多个自适应应用之间通信流的跟踪，而无需被跟踪应用做进一步的交互。

#### 4.3.3. LT 应提供跟踪点的接口

| 描述 | 日志应为应用软件和系统软件层面源代码中的跟踪点（**trace point**）提供一个接口。 |
| --- | --- |
| 理由 | 在软件开发和集成中，了解时序行为是必要且重要的。定义和收集由跟踪点发出的事件的可能性，是确定这种时序行为的基本特性。 |
| 适用平台 | **AP** |
| 用例 | * 跟踪系统级软件和应用级软件的动态状态<br>* 在源代码中提供跟踪点的 **API** 调用 |
| 依赖项 | - |
| 支撑材料 | - |

#### 4.3.4. LT 应发送建模的跟踪消息

| 描述 | 跟踪消息应通过建模的消息发送。 |
| --- | --- |
| 理由 | 在分布式系统中，经常需要确定跨多台 **ECU** 的分布式功能的时序行为。此外，能够比较不同的实现也很重要。使用建模的消息，可以使用可比较的格式，并以更少的开销（没有静态的、描述性的信息）发送跟踪信息。 |
| 适用平台 | **AP** |
| 用例 | 高效且标准化的跟踪格式 |
| 依赖项 | RS_LT_00002 |
| 支撑材料 | - |

| --- | --- |
| 理由 | 跟踪通常只在开发和集成期间需要。因此必须能够禁用它。在开发期间，可能只有若干应用值得关注。 |
| 适用平台 | **AP** |
| 用例 | 选择要跟踪的系统级和应用 |
| 依赖项 | RS_LT_00010, RS_LT_00005 |
| 支撑材料 | - |

#### 4.3.6. LT 应可配置为使用 ARTI 处理跟踪信息

| 描述 | 对于建模的跟踪消息，应可以配置定义 **ARTI** 来处理跟踪信息。 |
| --- | --- |
| 理由 | 通过使用 **ARTI** Trace **API**，可以将跟踪的开销降到最低。由于 **OS** 也使用 **ARTI** 进行跟踪，因此可以同时跟踪 **OS**、系统和应用层级。 |
| 适用平台 | **AP** |

| 依赖项 | RS_LT_00051 |
| 支撑材料 | - |
