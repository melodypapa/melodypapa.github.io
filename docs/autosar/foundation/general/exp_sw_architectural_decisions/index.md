## 1. 简介和功能概述

本说明文档为 AUTOSAR 标准所作的架构决策提供附加信息。

### 1.1. 目标

本文档的主要目标是为 AUTOSAR 标准所作的架构决策提供文档化，使这些决策在未来可被理解、可被评审，并最终使标准更易维护。

### 1.2. 范围

本文档涵盖为 AUTOSAR 标准的软件架构所作的决策。本文档的主要读者是 AUTOSAR 标准的架构师以及其他工作组的成员。

#### 5.1.1. PRS 文档变更对 AP 与 CP 的影响

| 依据 | 我们看到在不同的平台上使用不同协议版本的用例，例如 AP 可能同时支持"旧"版本与"新"版本，而 CP 只支持"旧"版本。同一协议版本的协议"特性"也是如此。 |
| 类别 | 无 |
| 是否影响应用 | 无 |
| 假设 | 未作假设。 |
| 约束 | AUTOSAR 遵循基于主干（**trunk-based**）的开发方式，没有任何缺陷修复分支。这意味着当前的 PRS 文档版本直接替代较旧的版本，不维护较旧的 PRS 文档版本。 |
| 备选方案 | 允许引用较旧的 AUTOSAR 发布——像 DLT v2 示例那样允许引用较旧的 AUTOSAR 发布。 |

| 备选方案 | 在单个文档中支持多个版本——如果 AUTOSAR 应支持多个协议版本，则它们应在同一发布的一个 PRS 文档中标准化。每个平台可以自行定义支持的程度。记录不同支持程度的一种方法是使用 SWS 的第 [4](#4-概述) 章来描述限制。 |
| 备选方案 | 在同一 AUTOSAR 发布中只支持一个版本——避免任何歧义，在一个 AUTOSAR 发布内只允许 AP 与 CP 都支持的一个 PRS 版本。 |
| 备注 | 无备注。 |
| 相关需求 | 无 |

### 5.2. 自适应平台

#### 5.2.1. 动态内存分配（Dynamic memory allocation）

| 字段 | 内容 |
|---|---|
| 适用平台 | AP |
| 决策 | 在设计 AUTOSAR 自适应平台标准时，允许并假定自适应应用和功能簇使用动态内存分配。 |
| 依据 | 由于 AUTOSAR 自适应平台标准采用 C++ 作为其 API 语言，动态内存分配的使用实际上是不可或缺的。由于 AUTOSAR 自适应平台标准将用于安全相关系统，动态内存分配可能导致非确定性行为。两个典型问题是碎片化以及不确定的分配/释放处理时间。为非安全关键系统设计的内存分配器常常表现出这些问题，因为它们在或多或少的程度上是为内存效率和/或平均处理性能设计的。这些问题可以通过使用确定性内存分配器来控制。内存分配是一个被充分研究的领域，已有多种技术被报道（一些例子见下文参考文献）。据报告，架构组内的多个 AUTOSAR 合作伙伴已经实现了此类确定性内存分配器，并将其用于量产系统。注意，此类分配器应替换标准 C 库提供的默认 malloc()/free() 实现——标准 C 库位于提供 new()/delete() 的 C++ 运行时库以及 AUTOSAR 自适应平台同样使用的 STL 之下。这使应用无需提供自己的自定义确定性分配器并将其安装到感知自定义分配器的类中。关于实时系统中内存碎片与内存分配的更多信息，请参见 [\[4\]](#ref-4)、[\[5\]](#ref-5)、[\[6\]](#ref-6) 和 [\[7\]](#ref-7)。 |
| 类别 | 安全（**Safety**） |
| 是否影响应用 | 否 |
| 假设 | 平台供应商和/或编译器供应商可以替换默认的内存分配/释放函数，以便在运行期的关键阶段——即出于安全目的需要这种确定性的阶段——使用这些函数的确定性版本。 |
| 约束 | 在运行期的某些阶段需要确定性。这些阶段正是需要将分配器替换为确定性版本的阶段。 |
| 备选方案 | 不使用动态内存分配——对于使用 C++ 而言，不使用动态内存分配不是一个备选项。 |
| 备选方案 | 将动态内存分配限制到特定阶段——在运行期中需要确定性的特定阶段禁止动态内存分配。这将使得在这些阶段运行复杂代码非常困难。 |
| 备注 | 无备注。 |
| 相关需求 | • [RS_AP_00129] 功能簇定义的公共类型应被设计为无需动态内存分配即可实现 |
| 发布 | R20-11 |

#### 5.2.2. 自适应运行时定义的类型应为 final（Types defined in the Adaptive Runtime for Applications should be final）

| 字段 | 内容 |
|---|---|
| 适用平台 | AP |
| 决策 | 自适应运行时类型应使用 final 说明符，除非它们意在用作基类。 |

| 类别 | 无 |
| 是否影响应用 | 否 |
| 假设 | 清晰地表达 AUTOSAR Runtime for Adaptive Applications 公共类层次的预期设计。 |
| 约束 | 未识别出约束。 |
| 备选方案 | 通过代码评审确保正确使用 AUTOSAR 类型——该备选方案是对使用 AUTOSAR 类型的应用代码进行代码评审。这完全超出 AUTOSAR 的范围，因此不是一个真正的备选项。 |
| 备注 | 无备注。 |
| 相关需求 | • [RS_AP_00140] 在 ara 类型中使用"final 说明符" |
| 发布 | R20-11 |

#### 5.2.3. out 参数的使用（Usage of out parameters）

| 字段 | 内容 |
|---|---|
| 适用平台 | AP |
| 决策 | out 参数可用于就地修改，但不得用于返回值。 |
| 依据 | 统一的外观与感受。C++ 核心指南 [\[8\]](#ref-8)："F.20：对于'out'输出值，优先使用返回值而不是输出参数。[...] 返回值是自说明的，而引用 & 既可能是输入输出也可能是仅输出，容易被误用。这包括像标准容器这样使用隐式移动操作以提升性能并避免显式内存管理的大型对象。" |
| 类别 | 无 |
| 是否影响应用 | 否 |
| 假设 | 在所有使用 API 的情形下都允许动态内存分配，即使运行时间关键的安全相关代码（包括 ASIL D）时也是如此。 |
| 约束 | 输入/输出参数（即在函数内修改一个已存在的参数）是允许的。例如，清除或写入缓冲区的函数应将该缓冲区作为非 const 的输入/输出参数接收。 |
| 备选方案 | 未考虑任何备选方案。 |
| 备注 | 无备注。 |
| 相关需求 | • [RS_AP_00141] out 参数的使用 |
| 发布 | R20-11 |

#### 5.2.4. 使用命名构造函数实现无异常对象创建（Usage of named constructors for exception-less object creation）

| 字段 | 内容 |
|---|---|
| 适用平台 | AP |
| 决策 | 返回 ara::core::Result 的无异常对象创建函数应使用"命名构造函数惯用法"（**named constructor idiom**）。 |
| 依据 | • 构造函数记号（**token**）类型是类的一个实现细节，因此不应被规定，甚至不应从外部访问。这使得必须使用 auto 来获取记号，因为记号类型无法以任何其他方式引用。• 必须非常小心地将记号的内容移动到 SomeClass 实例以满足"总是成功"的保证，如果需要获取多个资源，这可能很棘手。• 记号对象通过将其值 std::move 到 SomeClass 构造函数而"销毁"（实际上，按照 C++ 标准，它将处于一个"有效"但未指定的状态），但很容易误将它再次用于尝试创建另一个实例，导致未定义的结果。 |
| 类别 | 安全（**Safety**） |
| 是否影响应用 | 是 |
| 假设 | 未作假设。 |
| 约束 | 未识别出约束。 |
| 备选方案 | 构造函数记号方法——由于本决策依据中所述的缺点，未予考虑。 |
| 备选方案 | 常规构造函数调用——未予考虑，因为常规构造函数可能抛出异常，因而无法在无异常设计中使用。 |
| 备注 | 无备注。 |
| 相关需求 | 无相关需求。 |
| 发布 | R20-11 |

#### 5.2.5. 引入单调时钟 API（Introduction of a monotonic clock API）

| 字段 | 内容 |
|---|---|
| 适用平台 | AP |
| 决策 | AUTOSAR Runtime for Adaptive Applications 应提供自己的单调的 std::chrono::SteadyClock，表示机器的上电时间。该时钟的精度由平台供应商定义。该时钟的精度可以用作平台的特征值，使项目能够检查该时钟是否满足项目特定的需求（例如时间同步通常需要精度更高的时钟）。机器的系统启动定义了该时钟的纪元，因此该时钟表示机器的上电时间。处理时间戳或时钟的功能簇应以该时钟为基础。 |
| 依据 | 时间同步簇使用的时间戳应基于 std::chrono。时间同步需要一个具有特殊精度的单调时钟。 |
| 类别 | 无 |
| 是否影响应用 | 是 |
| 假设 | 由于时间同步报文只有一个通信端点，时间同步簇通常是基于守护进程（**daemon**）的架构。需要一个具有特殊精度的标准化时钟作为公共基础，以同步守护进程与库。 |
| 约束 | 未识别出约束。 |
| 备选方案 | 将时钟类型作为模板实参传递——所使用的时钟也可以作为模板实参传递。但在时间同步簇基于守护进程的情况下，无论如何都需要一个具有特殊精度的标准化时钟作为公共基础。 |
| 备注 | 单调时钟 API 通过 ara::core::SteadyClock 实现。 |
| 相关需求 | • [RS_AP_00130] AUTOSAR 自适应平台应表现一个丰富而现代的编程环境。 |
| 发布 | R20-11 |

#### 5.2.6. State Management、Execution Management 与 Platform Health Management 的职责（Responsibilities of State Management, Execution Management, and Platform Health Management）

| 字段 | 内容 |
|---|---|
| 适用平台 | AP |
| 决策 | State Management、Execution Management 与 Platform Health Management 是 AUTOSAR 自适应平台的基础。State Management、Platform Health Management 或 Execution Management 进程中的故障通常会典型地导致停止触发看门狗（**watchdog**）。Platform Health Management 监督 State Management 与 Execution Management。Platform Health Management 控制看门狗，因而反过来受硬件看门狗的监督。在自适应应用监督失败（即 Operating System/Execution Management/State Management/Platform Health Management 之外）的情况下，作为最后手段触发机器复位根本不应是一个选项。自适应应用中的监督失败应报告给 State Management。State Management 可以根据严重性将该失败转发给 Platform Health Management，以错误地触发或停止触发其服务的看门狗。Platform Health Management 对进程内或同一功能组内进程之间的检查点执行逻辑监督。Platform Health Management 向 State Management 报告任何监督失败。State Management 负责执行恢复动作，包括通过委托给自适应应用来切换功能组状态（**Function Group State**），或作为最后手段建议 Platform Health Management 执行硬件复位。Platform Health Management 用于监督安全关键进程。因此，对于非安全关键应用，Platform Health Management 是 AUTOSAR 自适应平台的可选部分。进程绝不应自行重启，因为它们可能具有未知的运行时依赖。进程与功能组之间的关系可以比作线程与进程之间的关系。即使在简单的/无依赖的情形下，State Management 也应始终触发一个请求（功能组状态变更）以重启进程。因此，Platform Health Management 与 Execution Management 之间没有直接接口。应移除 Platform Health Management 的不可恢复状态接口。 |
| 依据 | 所选方案使 Platform Health Management 的设计更简单，具有单一且明确定义的职责。所选方案同样遵循 State Management（控制系统状态）与 Execution Management（控制进程）的单一职责原则。恢复动作可以通过扩展（开闭原则）添加到 State Management。无需修改或配置 Platform Health Management。如果 State Management 选择将恢复委托给自适应应用，监督失败也可以由自适应应用处理。 |
| 类别 | 安全（**Safety**） |
| 是否影响应用 | 是 |
| 假设 | • State Management 是 AUTOSAR 自适应平台的必备部分。• 相对于执行合理的恢复动作（例如启动进程），经由 State Management 向自适应应用间接报告监督失败的性能影响/延迟可以忽略不计。 |
| 约束 | 未识别出约束。 |
| 备选方案 | 由 Platform Health Management 协调故障恢复——系统性故障的恢复由 Platform Health Management 协调。根据优先级涉及多个组件（自适应应用、Execution Management、State Management、看门狗）。Platform Health Management 按以下方式协调恢复：1. Platform Health Management 请求自适应应用恢复 2. 若失败，Platform Health Management 请求 Execution Management 重启失败的进程 3. 若失败，Platform Health Management 请求 State Management 通过切换功能组状态来恢复 4. 若失败，Platform Health Management 停止触发看门狗并复位机器 5. 若失败，Platform Health Management 切换到不可恢复状态（尚未完全定义）。由于多个组件对恢复动作负责、不符合单一职责原则，未考虑该备选方案。该方案还要求 Platform Health Management 具备应用知识，因为它必须在第 3 步确定适当的功能组状态。由于运行时依赖，重启单个进程可能并不合适（第 2 步）。 |
| 备选方案 | 分布式故障恢复——系统性故障的恢复由 Platform Health Management 与 State Management 协调。根据优先级涉及多个组件（自适应应用、Execution Management、看门狗）。Platform Health Management 与 State Management 按以下方式协调恢复：1. Platform Health Management 请求自适应应用恢复 2. 若失败，Platform Health Management 请求 State Management 通过重启应用来协调恢复 3. #### 5.2.19. 关于定义服务接口还是 C++ 接口的指导（Guidance whether to define a service or a C++ interface）

| 字段 | 内容 |
|---|---|
| 适用平台 | AP |
| 决策 | 选择服务接口还是 C++ 库接口，应基于与 API 消费者的接口可用性、自适应平台资源的高效使用以及通信所需能力相关的设计准则。在准则冲突的情况下，应通过库接口实现。该决策应考虑各种设计方面。偏向基于服务的接口设计的准则：• 使用可用于代码生成的建模数据类型。 • 支持面向服务通信的各种特性：服务接口提供方法（**method**）、事件（**event**）、触发器（**trigger**）、字段（**field**）等元素以满足特定类型的通信模式。此外，可以在单个服务接口中聚合这些元素中的任意类型。此类通信特性无法通过库接口提供。 • 支持通信端点的灵活发现——如果实现了服务接口，服务的消费者不必关心服务实例的位置。服务可能部署在不同的机器上。 • 专注于数据传输。偏向基于库的接口设计的准则： • 减少配置方面的工作量。 • 减少通信控制的开销——库接口不需要维护提供者与消费者之间的通信信道。某些类型的通信模式可能表现出更好的性能，例如不频繁的数据交换、点对点通信。 |
| 依据 | 质量要求提出"标准的使用对供应商和应用开发者而言应尽可能简单"。如果需要端点配置、服务发现或远程调用，使用服务的既有功能而不是单独的解决方案是明智的。质量要求还提出"整体方法不应被破坏（避免在一个标准中出现不同的方法）"。C++ 库接口更简单，可能更高效。它们还为实现留出更多自由，因为它们允许在自适应应用的进程中运行的实现。质量要求提出"规范应允许运行期高效的实现。运行期效率指所有资源消耗：CPU、RAM、ROM"。因此，在不确定服务接口是否有利时，应优先选择 C++ 库接口。 |
| 类别 | 无 |

| 假设 | 未作假设。 |
| 约束 | 未识别出约束。 |
| 备选方案 | 总是使用服务接口——优点：• 所有功能簇使用同类接口。缺点：• 对应用开发者而言并非总是最自然的方式。在不需要通信管理功能的情况下带来不必要的复杂性与实现限制。 |
| 备选方案 | 总是使用 C++ 库接口——优点：• 所有功能簇使用同类接口。缺点：• 对应用开发者而言并非总是最自然的方式。将需要针对服务发现与选择的单独解决方案。 |
| 备注 | 在调用方自适应应用的进程中运行的进程内实现只对具有 C++ 库接口的功能簇可行。具有服务接口的功能簇需要一个专门的进程。按照本决策，网络管理应提供 C++ 库接口。尽管如此，网络管理仍保持使用服务接口以维持向后兼容。 |

#### 5.2.24. 扩展接口的指南（Guidelines for Extension Interfaces）

| 字段 | 内容 |
|---|---|
| 适用平台 | AP |
| 决策 | 自适应平台应通过标准化的扩展接口（即所谓平台扩展接口（**Platform Extension Interface**））支持对其行为的扩展。平台扩展接口的实现例如由 OEM、集成者或其他第三方应用提供。此类扩展将以某种编程语言实现，不带任何代码生成支持，也不在清单（**Manifest**）中进行任何运行期配置。平台扩展接口的使用应限于这样一些情形：提供行为的一个实现比通过清单配置一个通用行为有充分理由。使用插件（**Plugin**）模式的平台扩展接口（参见 [\[2, EXP_SWArchitecture\]](#ref-2)，8.5.4 节）需要架构工作组的评审与批准。 |
| 依据 | 允许平台扩展接口的依据是自适应平台标准具有更好的可用性。特别是，以下质量属性的满足程度得到提升：• "AUTOSAR 自适应平台标准元素应易于使用且难以误用。"——因为在平台扩展接口适用的情形下，它们使用起来更方便。为平台扩展接口提供模式（参见 [\[2, EXP_SWArchitecture\]](#ref-2)，8.5.4 节）有助于满足以下质量属性：• "AUTOSAR 自适应平台标准应记录其决策，包括其依据与后果。" • "AUTOSAR 自适应平台标准应遵循整体方法并避免在一个标准中出现不同的方法。"平台扩展接口不干扰质量属性"应用开发者不应能够为预定义的平台功能提供自定义实现"，因为平台扩展接口的实现确实提供的是平台本身未提供的功能。 |
| 类别 | 无 |
| 是否影响应用 | 否 |
| 假设 | 假定通过清单对自适应平台协议栈实现进行完全定制并不能提供最佳可用性。对于某些变化点，假定提供行为的一个实现比配置一个通用行为更容易。在此类情形下，自适应平台需要通过由 OEM、集成者或其他第三方应用实现的标准化平台扩展接口来支持扩展。 |
| 约束 | 未识别出约束。 |

| 备注 | 平台扩展接口受支持的模式在 [\[2, EXP_SWArchitecture\]](#ref-2) 的 8.5.4 节中描述。 |
| 相关需求 | 无 |

#### 5.3.1. 结构体元素的顺序是标准的有约束力部分（The ordering of structure elements is a binding part of the standard）

| 字段 | 内容 |
|---|---|
| 适用平台 | CP |
| 决策 | SWS 定义的结构体元素的顺序被视为标准的一部分。因此，实现特定的优化（例如按大小对结构体元素重新排序以避免对齐间隙）不符合标准。 |
| 依据 | 偏离的结构体类型定义可能危害目标代码的互操作性。 |
| 类别 | 无 |
| 是否影响应用 | 是 |

#### 5.3.3. 不兼容 API 变更的指导（Guidance for incompatible API changes）

| 字段 | 内容 |
|---|---|
| 适用平台 | CP |
| 决策 | 如果 BSW 模块的函数需要不兼容的变更，API 名称的变更应基于以下决策矩阵：[变更] → [API 应更名（即新 API，旧 API 置为 obsolete）] [新增/移除参数且行为改变] → [是] [新增/移除参数且行为不变] → [否：直接变更、"缺陷"、"优化"] [更改既有类型/返回类型且行为改变] → [是] [更改既有类型/返回类型且行为不变] → [否] [函数行为的重大变更而不更改原型] → [是]。如果新 API 替代旧 API，旧的（被废弃的）API 应包含应改用哪个新 API 的信息。A) 对于不被其他 BSW 模块使用的外部 API，应适用以下生命周期变更：1. 引入新函数并将既有的旧函数置为"obsolete" 2. 在发布 +1 中：移除旧函数。B) 对于主要或专用于 BSW 模块之间的其他 API，变更应立即可见（直接变更既有函数，不设"obsolete"）。 |
| 依据 | 该方法提供最佳的向后兼容评级，并为用户提供迁移时间。 |
| 类别 | 无 |
| 是否影响应用 | 否 |
| 假设 | 被变更的函数是普通服务函数。Callout（原型由模块定义但代码不由模块定义的函数）可以用不同方式处理。 |
| 约束 | 无 |
| 备选方案 | 直接变更既有函数——也可以直接变更既有函数而不是新增函数。•（优点）如果只是新增/移除参数，则函数名称不变 •（缺点）不为用户提供迁移阶段。 |
| 备选方案 | 为未来的变更做好准备——如果已经知道该函数将来可能变更，则参数可以以标签/值对的形式提供。•（优点）允许为未来用例对参数进行兼容扩展 •（缺点）需要变长参数（"..."），会引起 MISRA 问题。 |
| 备注 | 本决策的缺点是新函数需要新的函数名。对于既有原型无法支持已定义行为的真实缺陷（"根本无法工作"），无需迁移阶段的直接变更更为可取。如果一个 C 类型被变更（例如结构体新增一个字段）且该类型出现在原型中，则该类型的变更被视为兼容。因此不需要强制变更函数原型（例如函数名）。（注：源文档中该决策的备选方案/备注/发布各行在 PDF→markdown 转换中严重乱序，此处按可读内容保守重组。） |
| 相关需求 | 无 |
