## 1. 文档范围

本文档规定健康监控（**Health Monitoring**）的需求。

对于本版本，本文档仅适用于自适应平台：与经典平台的对齐将在后续版本中完成。第 [5 章](#5-需求规格)中的「适用平台」字段应忽略。与经典平台的对齐将在后续版本中完成。

健康监控被 [\[1\]](#ref-1) 所要求（以控制流监控（**control flow monitoring**）、外部监控设施（**external monitoring facility**）、看门狗（**watchdog**）、逻辑监控（**logical monitoring**）、时序监控（**temporal monitoring**）、程序序列监控（**program sequence monitoring**）等术语），本规范旨在涵盖该标准中所有相关需求。

健康监控具有以下错误检测功能：

1. 存活监督（**Alive supervision**）——检查检查点（**Checkpoint**）是否以正确的频率发生
2. 期限监督（**Deadline supervision**）——检查两个检查点之间的时间差
3. 逻辑监督（**Logical supervision**）——检查检查点的执行序列是否正确
4. 健康状态监督（**Health status supervision**）——检查健康状态（**Health Status**）信息是否有效

健康监控还提供可配置的错误处理机制，以便从前述监督函数检测到的错误中恢复。

健康监督（**Health Supervision**）应由 **AUTOSAR** 经典平台和 **AUTOSAR** 自适应平台实现。它也可以由其他平台实现。

健康监督本身在 [\[2\]](#ref-2)（**ASWS Health Monitoring**）中规定，该文档规定了四个监督函数的实现无关行为/算法。系统健康监控允许跨多个 **AP**/**CP** 或非 **AUTOSAR** 平台聚合和转发健康信息。规范见 [2, ASWS Health Monitoring]，使用示例见 [3, EXP System Health Monitoring]。

## 3. 缩略语和缩写

以下收录与健康监控的规范或实现相关、且未被 [5, AUTOSAR glossary] 收录的缩略语和缩写。

**CM**
> **AUTOSAR** 自适应通信管理（**AUTOSAR Adaptive Communication Management**）

**DM**
> **AUTOSAR** 自适应诊断管理（**AUTOSAR Adaptive Diagnostic Management**）

**PHM**
> 平台健康管理（**Platform Health Management**）

**SE**
> 受监督实体（**Supervised Entity**）

**SHM**
> 系统健康监控器（**System Health Monitor**）

**Alive Counter**
> 存活计数器：检查点上下文中用于跟踪和处理其存活指示（**Alive Indication**）数量的独立数据资源。

**Alive Indication**
> 存活指示：受监督实体通过调用用于存活监督的检查点来表明其存活的指示。

**Alive Supervision**
> 存活监督：检查周期性受监督实体的时序约束是否处于所配置的最小和最大限值内的机制。

**Checkpoint**
> 检查点：受监督实体的控制流中报告活动的一个点。

**Deadline End Checkpoint**
> 期限结束检查点：配置了期限监督、并且是特定迁移的结束点的检查点。如果期限监督串联，一个检查点可以既是期限开始检查点又是期限结束检查点。

**Deadline Start Checkpoint**
> 期限开始检查点：配置了期限监督、并且是特定迁移的起始点的检查点。

**Deadline Supervision**
> 期限监督：检查从期限开始检查点到相应期限结束检查点的迁移执行时序约束是否处于所配置的最小和最大限值内的机制。

**Elementary Supervision Status**
> 基本监督状态：基于监督的评估结果（正确/不正确）表示存活监督、期限监督或逻辑监督当前状态的状态。

**Expired Supervision Cycle**
> 过期监督周期：存活监督未能通过其两个升级步骤的监督周期（存活计数器未通过预期存活指示数量（含容差）的次数超过允许的失败参考周期数）。

**Failed Supervision Reference Cycle**
> 失败监督参考周期：以存活计数器与预期存活指示数量之间检测到的偏差（含容差）结束的监督参考周期。

**Global Supervision Status**
> 全局监督状态：累计监督状态。在经典平台中，它汇总所有受监督实体的局部监督状态。在自适应平台中，它基于单个功能组（**Function Group**）内的一组基本监督状态计算得出。

**Graph**
> 图：通过迁移连接的一组检查点，其中至少一个检查点是初始检查点，并且图中任意两个检查点之间存在（经由迁移的）路径。

**Health Channel**
> 健康信道：提供（子）系统健康状态信息的信道。这可以是某个应用的全局监督状态、任何测试例程的结果，或（子）系统报告的状态（例如电压监控、**OS** 内核、**ECU** 状态等）。

**Health Channel Supervision**
> 健康信道监督：检查受监督软件注册的健康指示是否处于容差/限值内的监督类型。

**Health Monitoring**
> 健康监控：针对正确时序和序列的软件行为监督。

**Health Status**
> 健康状态：与受监督软件相关的一组状态（例如应用的全局监督状态、电压状态、应用状态、**RAM** 监控算法的结果）。

**Logical Supervision**
> 逻辑监督：检查软件（受监督实体或受监督实体集合）是否按程序员（所开发的代码）定义的序列执行的在线监督类型。

**Local Supervision Status**
> 局部监督状态：表示单个受监督实体的存活监督、期限监督和逻辑监督当前结果的状态。

**Platform Health Management**
> 平台健康管理：自适应平台的健康监控。

**Supervised Entity**
> 受监督实体：纳入监督的软件组件类型的整体或一部分。受监督实体表示相应软件组件类型内检查点的集合。一个软件组件类型可以包含零个、一个或多个受监督实体。受监督实体可以被多次实例化，此时每个实例被独立监督。

**Supervised Entity Identifier**
> 受监督实体标识符：在某个应用内唯一标识一个受监督实体的标识符。

**Supervision Counter**
> 监督计数器：受监督实体上下文中在每个监督周期内更新的独立数据资源，存活监督算法用它执行对已计数存活指示的检查。

**Supervision Cycle**
> 监督周期：执行周期性存活监督的时间段。

**Supervision Mode**
> 监督模式：微控制器或虚拟机的整体状态，或功能组的状态（自适应平台情形）。模式互斥。模式例如可以是 Startup、Shutdown、Low-power。

**Supervision Reference Cycle**
> 监督参考周期：存活监督用作参考以执行已计数存活指示检查（对每个受监督实体单独进行）的监督周期数量。

**Local Health Monitor**
> 局部健康监控器：收集其部署平台健康信息的局部健康监控器。

## 4. 功能概述

健康监控旨在监督受监督实体的执行：涉及时序约束（存活监督和期限监督）、涉及所需的执行序列（逻辑监督）以及涉及其健康（健康监督）。

健康监控可以对受监督实体执行，受监督实体可以是任何软件组件、软件组件组或自适应应用。

监督结果以及其他监控器（例如电压监控器）的输出可用于创建**健康指标**（**HealthIndicator**），为特性或子系统给出整体健康状态。

健康监控提供以下特性：

1. 对位于微处理器或虚拟机上、具有独立监督约束的多个单独受监督实体的监督。
2. 支持受监督实体的并行与并发执行以及多重实例化。
3. 支持不同的运行模式，软件组件的行为因模式而异。
4. 支持多个硬件看门狗。
5. 支持多种错误处理机制。

| 描述 | 健康监控应支持不同的看门狗实现，包括但不限于：<br>* 内部硬件看门狗（在微控制器中）<br>* 外部硬件看门狗<br>* 单独的专用芯片（**ASIC**）<br>* 单独微控制器上的一个应用 |
| --- | --- |
| 理由 | 不同的看门狗实现已经存在于市场上。 |
| 依赖项 | - |
| 适用平台 | **CP**、**AP** |
| 用例 | - |
| 支撑材料 | - |

##### 5.1.4.6. 健康监控应支持多个看门狗

| 描述 | 健康监控应支持多个看门狗，它们类型相同或不同，配置相同或不同。 |
| --- | --- |
| 理由 | 有些微处理器同时包含内部和外部看门狗用于监控，作为冗余机制。 |
| 依赖项 | - |
| 适用平台 | **CP**、**AP** |
| 用例 | 如果内部看门狗与 **CPU** 使用相同的时钟，那么由于使用相同的时钟，内部看门狗无法识别系统的「挂起」。为获得更高的鲁棒性，还需使用外部看门狗。 |
| 支撑材料 | - |

#### 5.1.5. 支持的错误处理机制

##### 5.1.5.1. 健康监控应能够上报监督错误

| 描述 | 作为可能的错误反应，健康监控应上报监督错误，提供检测到何种错误的信息。 |
| --- | --- |
| 理由 | 需要上报错误，以便对其进行记录和分析，或以便进行集中式错误反应。 |
| 依赖项 | - |
| 适用平台 | **CP**、**AP** |
| 用例 | 上报某个受监督实体违反了其存活监督但仍在限值内。上报整个微控制器处于需要复位的糟糕状态。由其他方处理健康监控上报的错误。 |
| 支撑材料 | - |

##### 5.1.5.2. 健康监控应能够错误地触发受服务的看门狗

| 描述 | 作为可能的错误反应，健康监控应能够错误地触发受服务的看门狗。 |
| --- | --- |
| 理由 | 为了提供微处理器的快速复位。 |
| 依赖项 | - |
| 适用平台 | **CP**、**AP** |
| 用例 | 微处理器。典型的看门狗错误触发包括：<br>* 立即生成对问题的答案（问答看门狗情形）<br>* 立即生成对看门狗的错误触发/通知（超时看门狗和窗口看门狗）<br>* 不生成答案（超时看门狗和窗口看门狗） |
| 支撑材料 | - |

##### 5.1.5.3. 健康监控应能够触发微控制器复位

| 描述 | 作为可能的错误反应，健康监控应触发微控制器复位，包括但不限于：<br>* 干净的微控制器复位（例如关闭所有服务、关闭套接字）<br>* 快速微控制器复位 |
| --- | --- |
| 理由 | 除错误触发看门狗外，这是健康监控可用于从故障系统状态恢复的第二种主要反应。 |
| 依赖项 | - |
| 适用平台 | **CP**、**AP** |
| 用例 | 健康管理器请求机器状态管理器执行复位。 |
| 支撑材料 | - |

#### 5.1.6. 与系统健康监控相关的特性

##### 5.1.6.1. 系统健康监控器应将健康指标作为标准化服务事件传输

| 描述 | 健康指标的传输应以标准化的方式、作为标准化服务事件的一部分完成。 |
| --- | --- |
| 理由 | 健康指标应以平台无关的标准化方式、作为服务/子系统的健康度提供给其他模块/平台，以便它们在平台级用于错误恢复/降级。 |
| 依赖项 | - |
| 适用平台 | **FO**、**CP**、**AP** |
| 用例 | 例如特性 **HAD** 分布在多个平台（**AP**、**CP** 和非 **AUTOSAR**）上。**SHM** 确定健康指标，并经由标准化的健康指标事件将其传输给使用特性 **HAD** 的组件。 |
| 支撑材料 | |

##### 5.1.6.2. SHM 应从局部健康监控器接收相关健康信息

| 描述 | **SHM** 应提供一个接口，通过各种通信机制接收健康指标和健康信息。 |
| --- | --- |
| 理由 | 接收到的信息用于确定系统级健康指标，**SHM** 需要支持信息接收。 |
| 依赖项 | - |
| 适用平台 | **FO**、**CP**、**AP** |
| 用例 | 特性 **HAD** 分布在多个平台（**AP**、**CP** 和非 **AUTOSAR**）上。**SHM** 需要这些平台的健康信息用于健康指标确定。健康信息例如可以包括由平台健康管理确定的监督状态。 |
| 支撑材料 | |

##### 5.1.6.3. SHM 与局部健康监控器之间的通信应受 E2E 保护

| 描述 | **SHM** 与局部健康监控器之间的通信应受 **E2E** 保护，从而是可靠的。 |
| --- | --- |
| 理由 | 交换的数据将用于安全关键决策，应受到保护以免受通信错误影响。 |
| 依赖项 | - |
| 适用平台 | **FO**、**CP**、**AP** |
| 用例 | 健康信息的不可靠传输可能触发不必要的降级策略。 |
| 支撑材料 | |

##### 5.1.6.4. SHM 实例之间的通信应受 E2E 保护

| 描述 | **SHM** 实例之间的通信应受 **E2E** 保护，从而是可靠的。 |
| --- | --- |
| 理由 | 交换的数据将用于安全关键决策，应受到保护以免受通信错误影响。 |
| 依赖项 | - |
| 适用平台 | **FO**、**CP**、**AP** |
| 用例 | 健康信息的不可靠传输可能触发不必要的降级策略。 |
| 支撑材料 | |

##### 5.1.6.5. SHM 与局部健康监控器之间的周期性通信应用于存活检查

| 描述 | 局部健康监控器与 **SHM** 之间的周期性交换对于存活判定是必要的。 |
| --- | --- |
| 理由 | 检测失效的平台或 **SHM** 实例很重要。如果通信配置有固定的周期时间，接收方可以通过将定期交换的健康信息用作心跳信号来检测失效的发送方。 |
| 依赖项 | - |
| 适用平台 | **FO**、**CP**、**AP** |
| 用例 | |
| 支撑材料 | |

##### 5.1.6.6. SHM 实例之间的周期性通信应用于存活检查

| 描述 | **SHM** 实例之间的周期性交换对于存活判定是必要的。 |
| --- | --- |
| 理由 | 检测失效的平台或 **SHM** 实例很重要。如果通信配置有固定的周期时间，接收方可以通过将定期交换的健康信息用作心跳信号来检测失效的发送方。 |
| 依赖项 | - |
| 适用平台 | **FO**、**CP**、**AP** |
| 用例 | |
| 支撑材料 | |

##### 5.1.6.7. SHM 应与平台无关

| 描述 | **SHM** 应可实现在 **AP**、**CP** 和非 **AUTOSAR** 平台上。 |
| --- | --- |
| 理由 | **SHM** 的集成是项目特定的，应提供关于在哪里部署 **SHM** 的最大灵活性，因为不同的安全考虑（例如 **ASIL** 等级）可能影响该决策。 |
| 依赖项 | - |
| 适用平台 | **FO**、**CP**、**AP** |
| 用例 | 多个 **SHM** 实例部署在 **E/E** 系统中。根据安全需要（**ASIL** 等级），它们可以部署在 **CP**、**AP** 和非 **AUTOSAR** 平台上。 |
| 支撑材料 | |

##### 5.1.6.8. SHM 应确定健康指标

| 描述 | **SHM** 应确定健康指标，即描述是否满足系统标称性能以及系统降级是否可能的指标。 |
| --- | --- |
| 理由 | 系统级健康指标是降级失效（**fail-degraded**）系统所需要的。 |
| 依赖项 | - |
| 适用平台 | **FO**、**CP**、**AP** |
| 用例 | 自动驾驶系统具有冗余信道。健康指标可由平台用于在一条信道失效时通过激活冗余信道作出反应。 |
| 支撑材料 | |

##### 5.1.6.9. SHM 应支持冗余概念

| 描述 | **SHM** 应以冗余机制实现。 |
| --- | --- |
| 理由 | 对于高度安全关键的功能，**SHM** 是单一故障点，因此应以冗余方式实现。 |
| 依赖项 | - |
| 适用平台 | **FO**、**CP**、**AP** |
| 用例 | 用于失效可运行（**fail-operational**）行为的多个 **SHM** 实例 |
| 支撑材料 | |

##### 5.1.6.10. SHM 应能够与非 AUTOSAR 软件平台交互

| 描述 | 需要与非 **AUTOSAR** 平台交换信息，以接收和提供健康指标。 |
| --- | --- |
| 理由 | 从系统健康的角度来看，没有理由将其仅限制于 **AUTOSAR** 平台，纳入例如来自 **GENIVI** 平台的健康信息可能是安全相关的。 |
| 依赖项 | - |
| 适用平台 | **FO**、**CP**、**AP** |
| 用例 | 自动驾驶系统使用非 **AUTOSAR** 平台实现从 **L3** 切换到 **L2** 功能的用户反馈。用户反馈是安全相关的，是系统健康分析所需要的。 |
| 支撑材料 | |

##### 5.1.6.11. SHM 应可在抽象平台描述信息内配置

| 描述 | **SHM** 可以使用抽象平台描述（**Abstract Platform Description**）提供的抽象接口描述。 |
| --- | --- |
| 理由 | 使用 **SHM** 的抽象描述是用 **AP** 和 **CP** 对平台无关行为建模的好方法。 |
| 依赖项 | - |
| 适用平台 | **FO**、**CP**、**AP** |
| 用例 | 使用不同平台的 **E/E** 系统。 |
| 支撑材料 | |
