## 1. 引言

**AUTOSAR** 文档中需求的表述遵循约束 TPS\_STDT\_00078 规定的表格，见 **Standardization Template** 的「Support for Traceability」章（[\[1\]](#ref-1)）。

需求的表达应使用约束 TPS\_STDT\_00053 规定的义务表达动词形式，见 **Standardization Template** 的「Support for Traceability」章（[\[1\]](#ref-1)）。

## 2. 方法论需求

本章提供需求的定义。

### 2.1. 通用需求

本节规定主要对两个平台都有效的通用需求。

#### 2.1.1. 主要需求

##### 2.1.1.1. 方法论应解释如何构建 AUTOSAR 系统

| 描述 | 方法论应解释如何使用活动和工件（**work product**）构建 **AUTOSAR** 系统。它应像一本用户手册，帮助组织高效地应用 **AUTOSAR**。特别地，方法论应解释如何构建由经典平台和自适应平台组成的系统。 |
| --- | --- |
| 理由 | 需要强有力的方法论来有效管理大型系统的构建。 |
| 依赖项 | - |
| 用例 | 工程师希望完成一项活动，并希望知道需要哪些输入、应使用哪些指导等。构建 **AUTOSAR** 系统的典型用例包括：<br>* **SWC** 实现<br>* **ECU** 集成<br>* 系统集成 |
| 适用平台 | **CP**、**AP** |
| 支撑材料 | - |

##### 2.1.1.2. 方法论应支持自顶向下和自底向上的方法

| 描述 | 方法论应同时支持自顶向下和自底向上的方法。在自顶向下的方法中，应考虑应用软件及其在 **ECU** 上分布的全部约束。在自底向上的方法中，应考虑来自硬件（**ECU**/传感器/执行器）的全部约束。 |
| --- | --- |
| 理由 | 改进集成阶段，并掌控嵌入式实时分布式系统中的复杂性。 |
| 依赖项 | - |
| 用例 | 如果在给定的车辆架构中新增一个 **ECU** 或用新的 **ECU** 替换既有 **ECU**，则集成期间需要把该 **ECU** 的所有新的或修改的资源纳入系统配置。 |
| 适用平台 | **CP**、**AP** |
| 支撑材料 | - |

##### 2.1.1.3. 方法论应支持构建同时包含 AUTOSAR 与非 AUTOSAR ECU 的系统

| 描述 | 方法论应支持构建由符合 **AUTOSAR** 的 **ECU** 和不符合 **AUTOSAR** 的 **ECU** 组成的系统。 |
| --- | --- |
| 理由 | 应支持完整车辆系统的设计。 |
| 依赖项 | - |
| 用例 | 既有 **ECU** 和 **LIN** 从节点需要与 **AUTOSAR** **ECU** 互操作。 |
| 适用平台 | **CP**、**AP** |
| 支撑材料 | - |

##### 2.1.1.4. 方法论应支持构建由多个 AUTOSAR 平台组成的系统

| 描述 | 方法论应支持构建由多个 **AUTOSAR** 平台组成的系统。 |
| --- | --- |
| 理由 | 应支持完整车辆系统的设计。 |
| 依赖项 | - |
| 用例 | 基于经典与自适应 **AUTOSAR** 平台的机器（或 **ECU**）之间的通信描述。 |
| 适用平台 | **CP**、**AP** |
| 支撑材料 | - |

##### 2.1.1.5. 方法论应支持不同利益相关方之间的数据交换

| 描述 | **AUTOSAR** 应定义用于在基于 **AUTOSAR** 车辆的开发期间、不同利益相关方之间进行数据交换的交换格式。交换格式应涵盖软件、网络拓扑和网络通信的描述。 |
| --- | --- |
| 理由 | 在开发过程中使用 **AUTOSAR** 模板 |
| 依赖项 | - |
| 用例 | 一个 **OEM** 提供软件接口描述和网络通信描述，并将其交付给供应商进行开发和集成。 |
| 适用平台 | **CP**、**AP** |
| 支撑材料 | - |

##### 2.1.1.6. 方法论应是模块化的

| 描述 | 利用流程组件。子流程应在自身上是完整且可测试的，以便在仍与既有工具和流程集成的同时，使用方法论的某些部分。 |
| --- | --- |
| 理由 | 更易于理解和验证方法论的各个部分。更易于管理修改，封装由变更引起的连锁反应，以允许迁移当前流程。更易于同时利用既有活动与 **AUTOSAR** 活动。应可以从某个中间活动开始，而不必从方法论的开头开始。模块化的方法论便于组织从其当前流程迁移或与之合并。模块化的方法论允许组织插入质量门（**quality gate**）等中间活动或其他检查，以及收集符合 **CMMI** 流程和/或 **SIL**-3 所需的度量。 |
| 依赖项 | - |
| 用例 | 某组织计划将一个 **AUTOSAR** **ECU** 引入其既有架构，但不打算使用系统模板及其相应活动和工件。他们计划直接从 **ECU** 层级开始。 |
| 适用平台 | **CP**、**AP** |
| 支撑材料 | - |

##### 2.1.1.7. 方法论应支持不同的抽象层级

| 描述 | 方法论应支持开发 **AUTOSAR** 系统的不同视图。这对应于参与系统开发的典型领域和相关方。 |
| --- | --- |
| 理由 | 改进集成阶段，并掌控嵌入式实时分布式系统中的复杂性。 |
| 依赖项 | - |
| 用例 | **AUTOSAR** 使用若干抽象层级来描述不同参与方之间交换的信息。例如在早期阶段只使用「虚拟功能总线」（**VFB**），而在后续开发阶段处理部署到多个 **ECU** 上的 **SWC** 的真实实现。 |
| 适用平台 | **CP**、**AP** |
| 支撑材料 | - |

##### 2.1.1.8. 方法论应支持往返工程

| 描述 | 方法论应支持往返工程（**round-trip engineering**）。这意味着为完成任务或工件可能需要若干次迭代循环。 |
| --- | --- |
| 理由 | 满足 **AUTOSAR** 质量需求。 |
| 依赖项 | - |
| 用例 | 汽车系统通常分若干样车阶段（A、B、C 等）开发。一个软件组件在 **AUTOSAR** 系统中被更新。只要迭代中没有发生相互矛盾的变更，更新后的 **ECU** 提取（**ECU Extract**）仍与既有的 **ECU** 配置匹配。 |
| 适用平台 | **CP**、**AP** |
| 支撑材料 | - |

##### 2.1.1.9. 方法论应支持 OEM 与供应商对 SW-C 结构的不同视图

| 描述 | 方法论应支持 **OEM** 与供应商之间的交互，其中 **OEM** 和供应商对 **SWC** 结构持有不同的视图。 |
| --- | --- |
| 理由 | 供应商调整 **SWC** 结构的可能性。 |
| 依赖项 | - |
| 用例 | **OEM** 将初始系统提取（**System Extract**）作为正式的需求规范交付给供应商。供应商扩展并重构该系统提取。在下一个开发周期中，**OEM** 将更新后的系统提取交付给供应商。此后供应商必须基于 **OEM** 所做的更新来更新其系统提取结构。供应商侧的变更量应限于 **OEM** 更新引起的变更。 |
| 适用平台 | **CP**、**AP** |
| 支撑材料 | - |

##### 2.1.1.10. 方法论应解释 OEM 对系统的不同视图的典型用法

| 描述 | 方法论应支持 **OEM** 对系统持有不同视图的用例。 |
| --- | --- |
| 理由 | 软件系统开发方法中方法论的一致性 |
| 依赖项 | - |
| 用例 | **OEM** 可能从功能角度构造 **AUTOSAR** 软件组件。然而，对于具体的车辆开发项目，需要 **SWC** 结构的拓扑视图。为了在生命周期中更好地处理，来自功能分解的 **SWC** 通过适当的映射被映射到拓扑视图。 |
| 适用平台 | **CP**、**AP** |
| 支撑材料 | - |

##### 2.1.1.11. 方法论应解释供应商对系统的不同视图的典型用法

| 描述 | 方法论应支持供应商对系统持有不同视图的用例。 |
| --- | --- |
| 理由 | 软件系统开发方法中方法论的一致性 |
| 依赖项 | - |
| 用例 | 供应商需要映射系统的不同视图，例如：a) 供应商已有一个既有软件架构。通过软件共享，一些组件被 **OEM** 交付的组件替代。b) 供应商需要正式描述表示不同版本的系统描述之间的变更。c) 供应商为不同 **OEM** 开发同一 **ECU**，因此需要将 **OEM** 的需求视图映射到其解决方案视图。d) 供应商用 2 个 **ECU** 实现 **OEM** 对一个 **ECU** 的定义，因此需要映射系统描述。 |
| 适用平台 | **CP**、**AP** |
| 支撑材料 | - |

#### 2.1.2. 编程语言

##### 2.1.2.1. 方法论应独立于编程语言

| 描述 | 方法论应通过提供通用解决方案而独立于编程语言。对于必然依赖编程语言的部分，这些小节应被显式注明并且是模块化的，使整体方法论可被裁剪以适配其他编程语言。 |
| --- | --- |
| 理由 | 通过恰当地构造方法论以支持既有和新兴的编程语言，方法论可以一致且成功地应用于整辆车。 |
| 依赖项 | - |
| 用例 | 为特定微控制器构建的 **ECU** 针对编程语言 ABC 显式优化。方法论解释何时以及如何规定和选择与所需编程语言兼容的软件组件实现。 |
| 适用平台 | **CP**、**AP** |
| 支撑材料 | - |

#### 2.1.3. 活动

##### 2.1.3.1. 方法论应允许引用工具的活动

| 描述 | 活动可以引用帮助完成该活动的工具。方法论应描述这些类型的工具及其使用时机。 |
| --- | --- |
| 理由 | 通过定义需要哪些工具，活动的执行者可以确保在活动开始之前所有工具都已被采购和安装。同时，**AUTOSAR** 特定工具的实现者可以清楚地了解其工具应支持哪些活动，并知道输入和输出工件是什么。这将有助于确保 **AUTOSAR** 工具的互操作性。 |
| 依赖项 | - |
| 用例 | 对于经典平台，活动「生成 **RTE**」需要一个 **RTE** 生成器工具和一个编译器。 |
| 适用平台 | **CP**、**AP** |
| 支撑材料 | - |

##### 2.1.3.2. 方法论应纳入行业标准工具的使用

| 描述 | 在存在编译器和链接器等行业标准工具的地方，方法论应将它们纳入。 |
| --- | --- |
| 理由 | 当行业标准工具已经存在时，**AUTOSAR** 不应要求使用特定工具。 |
| 依赖项 | - |
| 用例 | 编译器是行业标准工具。 |
| 适用平台 | **CP**、**AP** |
| 支撑材料 | - |

#### 2.1.4. 流程需求

##### 2.1.4.1. AUTOSAR 方法论不应绑定于特定的生命周期模型

| 描述 | **AUTOSAR** 方法论不应绑定于特定的生命周期模型。活动必须相对于其执行所处的开发流程的时间和阶段保持独立。 |
| --- | --- |
| 理由 | 与企业特定生命周期模型的连接：方法论应允许使用不同的生命周期模型，例如 **V** 模型、Rational 统一过程（**Rational Unified Process**）。 |
| 依赖项 | - |
| 用例 | 例如如果使用极限编程，测试用例在实现之前创建。对于大多数其他开发流程，实现在测试用例创建之前生成。 |
| 适用平台 | **CP**、**AP** |
| 支撑材料 | - |

##### 2.1.4.2. 应能够为每个工件添加精确且人类可读的文档

| 描述 | 方法论应允许为每个工件添加精确且人类可读的文档。该文档应是工件的一部分，或被唯一地引用。 |
| --- | --- |
| 理由 | 这对于记录无法从形式内容（例如名称）中显而易见地推导出的设计决策或限制是必要的。此类文档将提高质量或安全标准所要求的可追溯性。 |
| 依赖项 | - |
| 用例 | 选择冗余机制，例如 **NVRAM** 数据块的配置，可能与某条安全需求相关。这可能需要文字说明。 |
| 适用平台 | **CP**、**AP** |
| 支撑材料 | - |

##### 2.1.5.1. 方法论应支持不同绑定时间的参数配置

| --- | --- |
| 理由 | 需要关于绑定时间的稳定参考。 |
| 依赖项 | - |
| 用例 | 在 **AUTOSAR** 系统和 **ECU** 的开发期间，需要创建并最终选择特定的变体，例如预编译（**pre-compile**）或 post-build。 |

##### 2.1.5.3. 方法论应规定解析变体的任务

##### 2.1.5.4. 方法论应规定变体选择器值的工件

| --- | --- |
| 理由 | 这明确了变体选择器的值在哪里存储和维护。 |
| 依赖项 | - |
| 用例 | 可能的变体是预先已知的：它们在某个时刻被创建并作为一个工件被拥有，最终在选定变体时被消费。 |

### 2.2. 面向经典平台的需求

#### 2.2.1. 通用需求

##### 2.2.1.1. 方法论应支持 VFB 概念

| 描述 | 虚拟功能总线概念允许在完全抽象硬件的情况下，对 **SWC** 之间进行早期检查。方法论应包含该概念。 |
| --- | --- |
| 理由 | 改进集成阶段和并行开发。 |
| 依赖项 | - |
| 用例 | 在 **AUTOSAR** 中，一个应用被建模为互连组件的组合。**VFB** 是允许这些组件交互的通信机制。即使这些组件使用的资源在开发期间尚不可用（硬件/网络），也可以进行一些基本检查并提前解决一些问题，从而减轻后续集成阶段的负担。 |
| 适用平台 | **CP** |
| 支撑材料 | - |

##### 2.2.1.2. AUTOSAR 方法论应支持隐式通信行为概念

| 描述 | **AUTOSAR** 方法论应支持交换信息，以按照软件组件的需求配置 **RTE** 的隐式通信行为（**Implicit Communication Behavior**）。该信息可以在原子软件组件（**Atomic Software Component**）设计时首次定义，也可以在创建组合（**composition**）时添加。就隐式通信行为而言，原子软件组件的设计可以由隐式通信行为描述的蓝图（**blueprint**）引导。 |
| --- | --- |
| 理由 | 在自顶向下的设计方法中定义隐式通信行为需求 |
| 依赖项 | - |
| 用例 | - |
| 适用平台 | **CP** |
| 支撑材料 | RS_SWCT_03065、RS_STDT_00034 |

##### 2.2.1.3. AUTOSAR 方法论应解释数据交换点的描述与处理

| 描述 | 方法论应解释用于开发和使用数据交换点（**Data Exchange Point**）的工作流。例如，应描述 **AUTOSAR** 提供哪些制品来支持数据交换点 profile 的开发，这些 profile 可用于分析潜在的工具互操作性问题，或按照所描述的数据交换点配置 **AUTOSAR** 工具的验证引擎。 |
| --- | --- |
| 理由 | 工具互操作性 |
| 依赖项 | [§2.2.1.4](#2214-autosar-方法论应将模板与分布式开发流程相关联) |
