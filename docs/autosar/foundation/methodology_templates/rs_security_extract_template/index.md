## 1. 引言

### 1.1. 本文档的范围

本文档收集对安全提取模板（**Security Extract Template**）的需求。

安全提取（**Security Extract**）的主要目的是定义安全事件（**Security Event**）及其属性，作为车辆电子电气入侵检测系统（**IDS**）的输入。安全提取可以作为交换文件，在开发过程中以及车辆已在现场运行时的维护过程中，从多个来源收集安全事件及其属性。

安全提取文件用于配置车辆 **ECU** 或机器（**Machine**）中入侵检测系统管理器（**IdsM**）实例的安全事件。

它还可以进一步用作（例如）「安全事件与事件管理」（**SIEM**）系统的输入，作为「安全运营中心」（**SOC**）的一部分，以便解读从车辆的 **IdsM** 实例接收到的二进制数据。

简而言之，使用安全提取的关键方面是：

- 在开发过程中从多个来源收集安全事件定义
- 作为车辆 **ECU** 与机器的 **IdsM** 实例的安全事件配置的输入
- 作为 **SIEM** 系统的输入，以便解读与安全事件相关的二进制数据

### 1.2. 文档约定

**AUTOSAR** 文档中需求的表述遵循约束 TPS\_STDT\_00078 规定的表格，见 **Standardization Template** 的「Support for Traceability」章（[\[1\]](#ref-1)）。

需求的表达应使用约束 TPS\_STDT\_00053 规定的义务表达动词形式，见 **Standardization Template** 的「Support for Traceability」章（[\[1\]](#ref-1)）。

### 1.3. 指南

应引用既有规范（以单一需求的形式）。与这些规范的差异作为附加需求规定。

所有需求应具有以下属性：

- 冗余性（**Redundancy**）

需求不得在一个需求内部或其他需求中重复。

- 清晰性（**Clearness**）

所有需求只允许一种解释。使用的、术语表中没有的技术术语必须加以定义。

- 原子性（**Atomicity**）

每个需求应只包含一条需求。如果一个需求无法再拆分为更多需求，则该需求是原子的。

- 可测试性（**Testability**）

需求应能够通过分析、评审或测试加以检验。

- 可追溯性（**Traceability**）

需求的来源和状态应始终可见。

### 2.3. 与 AUTOSAR 方法论相关的需求

#### 2.3.1. 支持 IDS 作用域和系统边界的定义

| 描述 | 安全提取应支持定义处于设计和实现中的 **IDS** 的作用域（即系统边界）。 |
| --- | --- |
| 理由 | 一个 **IDS** 设计通常涉及车辆内所有 **ECU** 的一个子集。该子集中的每个 **ECU** 应能够上报单独定义和/或适配的安全事件。因此，为了开发 **IDS**，安全提取需要能够定义属于一个 **IDS** 的所有系统部分以及这些 **IDS** 系统部分的特定系统级能力。 |
| 用例 | **IDS** 的系统级描述 |
| 依赖项 | - |
| 支撑材料 | |

| 描述 | 安全提取应支持其定义在开发伙伴之间的部分交换和完整交换。 |
| --- | --- |
| 理由 | 为了实现 **IDS** 的分布式开发，多个开发伙伴共同为一个描述整个 **IDS** 设计的安全提取文件作贡献。这些贡献者需要能够在 **IDS** 设计允许的范围内，尽可能独立于其他人地指定他们负责的安全提取部分。 |
