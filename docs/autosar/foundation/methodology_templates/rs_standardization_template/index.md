## 1. 简介

**AUTOSAR** 模型在许多情况下并非从零创建，而是以既有内容为基础。既有内容可以由 **AUTOSAR** 组织本身以标准化模型元素的形式提供。

本文档规定对标准化模板（**Standardization Template**）的需求。该模板旨在支持 **AUTOSAR** 交付标准化的模型元素。

**AUTOSAR 4.0** 已经规定了用于标准化的蓝图（**blueprint**）方法。标准化模板延续并改进了该方法。由此它将取代软件组件模板 [\[1\]](#ref-1) 中的附录 A。

作为一个具体示例，让我们考虑应用接口的标准化。即，就 **AUTOSAR** 元模型而言，标准化主要适用于为特定目的定义 PortPrototype。

由于 **AUTOSAR** 元模型的结构，仅仅表达一个标准化的 PortPrototype 是不可能的，因为有充分的理由，后者并不独立存在，而是始终由一个 SwComponentType 拥有。

标准化模板规定了克服这种情形的方法。

### 1.1. 文档约定

**AUTOSAR** 文档中需求的呈现遵循 TPS_STDT_00078 中规定的表格，参见标准化模板的「可追溯性支持（**Support for Traceability**）」章节（[\[2\]](#ref-2)）。

应使用 TPS_STDT_00053 中规定的表达义务的言语形式来表示需求，参见标准化模板的「可追溯性支持」章节（[\[2\]](#ref-2)）。

### 1.2. 指南

现有的规范应被引用（以单个需求的形式）。与这些规范的差异被规定为附加需求。所有需求应具有以下属性：

- 冗余性（**Redundancy**）

  需求不得在单个需求内或其他需求中重复。

- 清晰性（**Clearness**）

  所有需求应当只允许一种解释。所使用的、不在术语表中的技术术语必须被定义。

- 原子性（**Atomicity**）

  每条需求应只包含一个需求。如果一个需求无法被进一步拆分为更多需求，则它是原子的。

- 可测试性（**Testability**）

  需求应当可以通过分析、评审或测试来验证。

- 可追溯性（**Traceability**）

  需求的来源和状态应当始终可见。

## 2. 用例

本章描述标准化模板的用例。这些用例的意图是指出标准化模板的潜在应用。总体上，标准化模板的用例是将 **AUTOSAR** 标准化的条目表达为 **AUTOSAR XML** 工件。该工件随后可用于支持开发符合 **AUTOSAR** 的产品。

本文档中定义的每个用例都有其唯一标识符，以前缀 `UC_STDT_`（表示 Standardization Template Use Case）开头。

### 2.1. 支持应用接口

**AUTOSAR**：为不同领域（例如底盘、动力总成、车身等）提供标准化、公开披露的接口。这些接口的定义可以在不同的深度层级上处理：

- L8：**SWC** 的完整描述，包括行为模型和端口
- L7：所有端口的完整描述，包括接口行为和数据质量
- L6：所有端口的完整描述，包括接口行为和数据质量的文字描述
- L5：所有端口的完整描述，包括接口的数据质量
- L4：所有端口的完整描述，包括在 **AUTOSAR** 内商定的数据质量
- L3：**SWC** 的端口/接口的部分描述，包括在 **AUTOSAR** 内商定的数据质量

请注意，这一部分描述既包括只描述了部分端口的事实，也包括对端口的描述是不完整的、并且与适用的组件相分离的事实。这也被称为 PortBluePrint。

- L2：接口字典，包括一组在 **AUTOSAR** 内商定的数据质量
- L1：数据元素字典，包括类型和范围。
- L0：名称字典

从 4.0 版本起，**AUTOSAR** 标准化覆盖 L0 … L3 层级。尽管如此，供应商内部应用也可能将标准化模板用于更高的层级。

该用例主要覆盖应用软件方面。

应用这种形式化描述将提高 **AUTOSAR** 应用接口的一致性和可用性，并支持形式化检查，例如应用接口的向后兼容性检查。

### 2.2. 表达 SWS 的部分内容

标准化模板应当允许使用 **AUTOSAR** schema 形式化地表达基础软件模块 SWS 的部分内容。这包括（但不限于）：

- 标准化接口（即 C 语言 **API**）
- 标准 **AUTOSAR** 接口（端口、端口接口等）
- **ECUC** 参数的定义（见 [2.3](#23-标准化-ecuc-参数定义)）

应用这种形式化描述将提高 **AUTOSAR** SWS 的一致性和可用性，并支持形式化检查，例如接口的向后兼容性检查。

### 2.3. 标准化 ECUC 参数定义

**AUTOSAR** SWS 的组成部分还包括 **ECU** 配置参数定义的集合。这些参数定义是所谓的供应商特定参数的基础，后者用于具体的 **AUTOSAR** 实现中。

尽管这在 [\[5\]](#ref-5) 中有非常详细的规定，它同样在标准化模板的范围之内。

### 2.4. 表达预定义路径

开发伙伴可以就特定的包布局达成一致，从而在开发的后期阶段共享 **AUTOSAR** 工件。对于该用例，预先表达一组预定义或部分预定义的引用路径（reference path）或引用基（referenceBase）会很有帮助，它们可以被加载到各个 **AUTOSAR** 制作工具中。

该用例覆盖引用路径的开头或结尾。例如，用例是在一个可变路径之后标准化子结构：&lt;MyPath&gt;/PortInterfaces。在这种情形下只有 PortInterfaces 被标准化。

### 2.5. 表达平台类型

[\[6\]](#ref-6) 中定义的平台类型需要以可供 **AUTOSAR** 开发工具处理的格式提供。这种方法提高了 **AUTOSAR** 产品的一致性和质量。

适用 [\[7\]](#ref-7) 第 3.1 章的细节。

### 2.6. 表达已应用标准的示例

除了应用接口 [\[8\]](#ref-8) 之外，**AUTOSAR** 还提供如何应用标准化元素（特别是蓝图）的示例。

适用 [\[7\]](#ref-7) 第 3.1 章的细节。

### 2.7. 支持验证实现是否符合已定义的标准

在开发 **AUTOSAR** 产品时，可以通过将产品与形式化的标准进行验证来执行初始验证。这包括：

- 检查蓝图与派生模型元素之间的兼容性规则。这些兼容性规则要为每个有资格进行蓝图化的元类定义。
- 在模型元素与 SWS 或蓝图之间进行追溯，以检查是否实现了所有蓝图。

请注意，该用例是一种非常初始的验证，不与符合性测试规范竞争，更不能取代它。它只是为符合性测试做出贡献。

兼容性规则只需要在文档中描述，例如以约束的形式。元模型中不存在兼容性规则的形式化表示。

兼容性规则针对每个有资格进行蓝图化的元类单独规定。例如，所有端口蓝图遵循相同的兼容性规则。

### 2.8. 支持可复用的文档

**AUTOSAR** SWS 的部分内容可以被发布，使其能够被复用于实际的产品文档。实现的供应商随后从标准化模板的一个实例中取出这些部分，并将其纳入自己的软件文档中。

同样的方法也适用于应用接口的解释。

### 2.9. 定义命名约定

**AUTOSAR** 拥有建模指南和命名约定。如果这些约定作为标准化模板的实例发布，它们可以用于配置建模工具等。

该用例还覆盖表达不同义务层级的能力。这可以例如以类似于关键字 "**MUST**"、"**MUST NOT**"、"**REQUIRED**"、"**SHALL**"、"**SHALL NOT**"、"**SHOULD**"、"**SHOULD NOT**"、"**RECOMMENDED**"、"**MAY**" 和 "**OPTIONAL**" 的方式表达。

### 2.10. 在超出 AUTOSAR 范围的层级上执行标准化

标准化模板应当适用于公司内部的标准化或超出元层级 M1 上 **AUTOSAR** 标准化范围的双边协议（参见 [2.1](#21-支持应用接口)）。

> 关于元层级的更多细节见 [\[7\]](#ref-7) 第 2.2 章。

### 2.11. 通过手动更改属性从蓝图派生对象

用户制作一种蓝图的副本，并被允许添加自己的内容（例如向标准化的枚举类型添加自己的字段）。示例是 ApplicationInterfaces 和 ConfigurationParameters 的使用。

对于 **AUTOSAR** 服务的标准化端口接口，标准化模板应当提及如下用例：在这种情形下，基于「标准化端口接口蓝图」的端口接口可以包含 ClientServerOperations 的一个子集。

### 2.12. 以完全标准化的方式从蓝图派生对象

用户只能以完全标准化的方式配置或以其他方式影响所复制的「蓝图」的内容（例如根据软件的「需要」配置枚举类型的字段），而不能添加自己的内容。

这甚至可以走到这样的程度：只有配置的规则被标准化（如 **DCM** 端口接口的情形）——但这仍然完全决定了具体项目中的结果。

### 2.13. 集成编译测试

在 4.0 版本之前，所有 **BSW** 的 **API** 都被建模，SWS 的第 8 章主要从模型生成。此外，我们建议从模型生成空的 C 语言函数（以及数据结构/常量等），并将所有这些函数链接在一起。如果编译或链接过程失败，则一致性（例如不同 SWS 之间的）被违反，需要修复。

### 2.14. 从模型生成 BSW「标准 AUTOSAR 接口」描述

在 4.0 版本之前，「标准 **AUTOSAR** 接口」是提供该接口的每个 SWS 的一部分（通常包含在第 7 或第 8 章的一个单独的子章中）。该描述主要是纯文本，带有一些展示接口用法（包括常量等）的伪语言。此外，服务的描述经常使用元模型中已过时或含义已变化的「元素」。

计划将 SWS 的这一部分标准化，例如通过一个自己的模型（然后生成的描述可以像第 8 章那样导入 SWS），或者通过一种（标准化的）语言来澄清对接口的理解，并为 **RTE** 目的允许自动转换。

### 2.15. 处理通用规范项

可能存在一组需要由所有 SWS 文档满足的通用需求。另一方面，可能存在一个汇总所有通用规范项的通用规范。这种情形应通过追溯来处理：

- 追溯应同时使用两份需求文档，即通用文档和单独文档。
- 通用需求可以由通用规范或由单独规范满足。
- 通用需求可能不适用于某个特定规范。
- 通用需求可能只有由通用规范和单独规范一起才能完全满足。

### 2.16. 在 AUTOSAR 中管理需求

在 **AUTOSAR** 中，所有需求都以唯一的 id 形式化地记录在需求文档（RS/Feature/SRS）中。规范文档（SWS）包含形式化地追溯到需求的规范项。同一层级的需求之间的依赖关系在需求块本身中通过提供对需求的引用来表达。

### 2.17. 在 AUTOSAR 中管理规范项

在 **AUTOSAR** 中，所有规范项都以唯一的 id 形式化地记录在规范文档（TPS、SWS）中。规范项形式化地追溯到需求。

### 2.18. 在 AUTOSAR 中管理约束项

在 **AUTOSAR** 中，所有约束项都以唯一的 id 形式化地记录在规范文档（TPS、SWS）中。

### 2.19. 在 AUTOSAR 中管理测试项

在 **AUTOSAR** 中，所有测试项都以唯一的 id 形式化地记录在规范文档中。

### 2.20. 描述数据交换点

描述：一种机器可读的语言，允许描述一个数据交换点。该语言本质上是为某种预期用途选择 **AUTOSAR** 模板的一个子集。

后置条件：数据交换点的描述可用。

参与者：Profile 作者。

指南：Profile 制作工具。

- 基本流程：
  1. 描述概览和管理数据（例如工具、输入/输出、引用的资产、引用的 **AUTOSAR** 版本）
  2. 描述方法论中的工件（例如引用工件「**ECU** 系统描述」）
  3. 描述预期用途（例如以自由文本形式非正式地描述「创建一个 **ECU** 抽取，并为非分段发送和接收配置 **CAN** 通信栈」）
  4. 描述元模型的相关子集（例如列出与预期用途可能相关的元类和元属性名称）
  5. 描述相关约束（例如列出相关约束 **ID**）
  6. 描述相关规范项（例如列出相关规范项 **ID**）
  7. 描述模型的相关子集（例如标识根元素以及展示如何找到模型相关部分的查询）
  8. 描述被排除的模式（例如显式排除元类、元属性、枚举值、CATEGORY 等）
  9. 描述完整性（例如描述最小多重性或约束）
  10. 描述默认值（例如何时应用 **AUTOSAR** 定义的默认值的条件：「不应用」「值缺失时总是应用」「从无法表达该值的模型的版本更新时应用」等）
  11. 描述职责（例如通过标识消费者保证完整性的模型子集的查询）
  12. 记录决策的理由以便维护和复用（例如一组彼此关联的 profile 部分的引用。该组包含诸如「特性 a 所需」之类的文档）

### 2.21. 在 AUTOSAR 中管理建议项

在 **AUTOSAR** 中，所有建议项（**advisory item**）都以唯一的 id 形式化地记录在规范文档（TPS）中。

## 3. 需求
